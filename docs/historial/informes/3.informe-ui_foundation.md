## El QUÉ — qué se construyó

La **base del design system** (el conjunto de estilos y componentes reutilizables con el que se van a
construir todas las pantallas). Antes el proyecto solo tenía backend (datos, API, lógica) y una página
"pelada" sin estilos. Ahora existe la infraestructura visual:

- El **contrato de identidad** (colores, tipografías, espaciados, sombras…) cargado como **tokens**
  (variables con nombre, p. ej. `--accent` en vez de repetir el rosa `#E4649B` por todos lados).
- Las **tres tipografías** de la marca cargadas de forma **self-hosted** (servidas por la propia app, sin
  pedirlas a un servidor externo en cada visita).
- Los **tres primitivos base** — **Button** (botón), **Field/Input** (campo de formulario con etiqueta y
  mensaje de error) y **Card** (tarjeta contenedora) — listos para usarse, con sus variantes y estados.
- Un helper `cn()` para combinar clases de estilo sin conflictos.

Con esto, la feature #13 (shell + navegación) y todas las páginas ya tienen sobre qué montarse.

## El CÓMO — cómo se construyó

- **Tokens → Tailwind v4.** Se portaron **todos** los valores de `template/tokens.css` a
  `src/app/globals.css` dentro de un bloque **`@theme`** (la forma que tiene **Tailwind CSS v4** —el
  framework de estilos utility-first— de declarar tokens de diseño y generar utilidades a partir de ellos).
  No hay `tailwind.config.*`: en la v4 el tema se define en el propio CSS. Un `postcss.config.mjs` con el
  plugin `@tailwindcss/postcss` es lo que compila ese CSS.
- **Alias `--color-*`.** Los tokens de rol del SDD (`--accent`, `--fg`, `--border`…) no viven en el
  "namespace de color" que Tailwind usa para fabricar utilidades como `bg-accent`. Se añadió un bloque de
  alias `--color-<rol>: var(--<rol>)` que **no inventa valores nuevos** (solo apunta a los tokens ya
  definidos) y habilita esas utilidades limpias. Los nombres exactos del SDD §5 siguen presentes para quien
  prefiera consumirlos con `var(--token)`.
- **Fuentes con `next/font`.** Se cargaron con `next/font/google` (utilidad de Next.js que **descarga la
  fuente en tiempo de build y la sirve desde la propia app**, evitando el "parpadeo" de texto y las
  peticiones a Google en runtime): Instrument Serif (display + énfasis en itálica), Archivo (cuerpo) e IBM
  Plex Mono (monoespaciada, para datos/ASCII). Cada una expone una **variable CSS generada** que los tokens
  `--font-display/body/mono/emphasis` referencian.
- **Primitivos con `cva`.** Cada componente separa sus variantes en un archivo `<name>.variants.ts` usando
  **`class-variance-authority`** (librería que declara combinaciones de clases tipadas: `variant`
  primary/secondary/ghost/danger, `size`, etc.) y fusiona cualquier `className` externo con `cn()` =
  `twMerge(clsx(...))` (evita que dos clases de Tailwind en conflicto peleen). **Field** es Client Component
  porque usa `useId` para cablear accesibilidad (asociar etiqueta↔input, `aria-invalid`, `aria-describedby`).
- **Cero hardcode, garantizado por test.** Un test guardrail (`no-hardcode.test.ts`) escanea los archivos de
  componente y **falla** si encuentra un hex, un `rgb()/rgba()` o un `px` crudo: obliga a que todo pase por
  token. Donde el template traía un valor suelto (un padding en px, el color de disabled) se **ajustó a la
  escala de tokens** (`--space-*`, `--fg-muted`) o se derivó con `calc()`/`color-mix()` sobre tokens.

## El PORQUÉ — por qué así y no de otra forma

- **Token-first es regla dura** (`conventions.md` + SDD §2/§5): cambiar la identidad visual debe ser cambiar
  tokens, no perseguir valores por 50 componentes. Por eso el guardrail automatizado en vez de confiar en la
  disciplina manual.
- **Tailwind v4 con `@theme` y sin config** es el modelo nativo de la v4 y el que pide RFC-01 §3; evita
  mantener dos fuentes de verdad (CSS + JS de config).
- **`next/font` self-hosted** lo exige el SDD §3 y RFC-01 §3 (sin FOUT, sin requests externos).
- **No romper el backend:** vitest se dejó con `environment: "node"` por defecto (los 281 tests de datos/API
  corren en Node, no en un DOM simulado). Los tests de UI declaran `// @vitest-environment happy-dom` archivo
  por archivo — **happy-dom** es un DOM ligero simulado donde React Testing Library puede montar y probar
  componentes. Cambiar el default global habría intentado correr los 281 tests de backend en un DOM y los
  habría roto.
- **Alcance acotado a 3 primitivos:** el acceptance de #12 pide solo Button, Field/Input y Card. El resto del
  inventario (Emphasis, ArchiveNav, Toggle, Dialog…) pertenece a #13/#14 y a las páginas — meterlos acá
  habría sido scope creep y habría mezclado dos features.

## El DÓNDE — dónde vive el código

**Configuración / build**
- `postcss.config.mjs` — activa el plugin de Tailwind v4.
- `src/app/globals.css` — `@import "tailwindcss"` + `@theme` con todos los tokens + alias `--color-*` +
  mapeo de fuentes + estilos base (body con `--bg`/textura, `::selection`, media `prefers-reduced-motion`).
- `src/app/layout.tsx` — carga las 3 fuentes con `next/font` y aplica sus variables al `<html>`; importa
  `globals.css`.
- `vitest.config.ts` — añade `setupFiles`; **default sigue `node`**.
- `vitest.setup.ts`, `src/shared/ui/testing/vitest-axe.d.ts` — matchers de jest-dom + `toHaveNoViolations`.
- `package.json` / `pnpm-lock.yaml` — stack nuevo (Tailwind v4, cva, tailwind-merge, clsx; testing: RTL,
  user-event, jest-dom, happy-dom, vitest-axe).

**Design system (`src/shared/ui/`)** — presentación pura, portable, no toca datos ni backend
- `lib/cn.ts` — helper `cn()`.
- `primitives/button/` — `Button.tsx` + `button.variants.ts` + `index.ts` + `Button.test.tsx`.
- `primitives/field/` — `Field.tsx` + `Input.tsx` + `index.ts` + `Field.test.tsx`.
- `primitives/card/` — `Card.tsx` + `card.variants.ts` + `index.ts` + `Card.test.tsx`.
- `primitives/index.ts`, `index.ts` — barrels (API pública del design system).
- `primitives/no-hardcode.test.ts` — guardrail token-first (env node).

## Deuda o notas abiertas (no bloquean)

1. **Breakpoints para variantes responsive.** Están portados como `--bp-*` (nombres SDD). Para usar prefijos
   responsive de Tailwind (los necesitará el nav de #13) habrá que exponerlos también en el namespace
   `--breakpoint-*`. Se hará en #13.
2. **Resto del inventario SDD §6 sin portar** (IconButton, Textarea, Select, Toggle, Badge, Tabs, Dialog,
   Tooltip, Toast, Emphasis, Progress, Skeleton, Spinner): se irán portando en las features que los necesiten.
3. **Gotcha registrado:** en `globals.css`, un comentario que contenía `bg-*/text-*` rompía el build porque
   `*/` cerraba el comentario CSS antes de tiempo. Evitar la secuencia `*/` dentro de comentarios de tokens.

## El QUÉ — qué se construyó

El **caparazón (shell) de la app**: el marco visual persistente dentro del que van a vivir todas las
páginas. Antes solo existían la base de estilos y tres primitivos (feature #12) y una home pelada. Ahora hay:

- **AppShell** — la estructura de página: barra de navegación arriba (en tablet/desktop), el contenido en el
  medio, una barra inferior de accesos en mobile, y un **hueco reservado detrás del contenido para la escena
  3D** (que llega en la feature #14; acá queda el espacio, no el objeto).
- **ArchiveNav** — la navegación "archivero" (pestañas tipo carpetas de fichero, estética de la marca) con las
  **6 secciones** de la app; la carpeta activa se resalta **según la URL actual**.
- **BottomNav** — la misma navegación en formato barra inferior táctil para pantallas chicas (mobile).
- **Route groups** `(app)` y `(auth)` — dos "zonas" de la app: la privada (envuelta por el shell) y la de
  autenticación (pantalla limpia, sin nav).
- El nav muestra el **nombre del usuario** (leído del backend) y un botón **Salir** (logout).

## El CÓMO — cómo se construyó

- **Navegación activa por ruta.** Los componentes de nav son **Client Components** (componentes que corren en
  el navegador, necesarios porque leen la URL en vivo) y usan `usePathname()` de Next.js para saber en qué
  ruta está el usuario. Un helper `isRouteActive(pathname, href)` decide la activa: coincidencia **exacta**
  para la raíz `/` (Dashboard) y por **prefijo** para el resto (así `/proyectos/42` marca "Proyectos"). La
  activa lleva `aria-current="page"` (atributo que anuncia a lectores de pantalla "esta es la página actual").
  Se descartó el *scroll-spy* del template (marcar según scroll) porque acá la verdad es la ruta.
- **Route groups de Next.** `(app)` y `(auth)` son carpetas entre paréntesis: **agrupan sin cambiar la URL**.
  `src/app/(app)/layout.tsx` envuelve todo lo privado con el shell; la home se **movió** a
  `(app)/page.tsx` (sigue siendo `/`, ahora dentro del shell). `(auth)/layout.tsx` es el layout limpio.
- **Costura de pureza (la decisión arquitectónica central).** El design system (`src/shared/ui/`) es
  **presentación pura** por contrato (SDD §2): no hace peticiones al backend, no conoce rutas ni endpoints.
  Por eso el AppShell/ArchiveNav **reciben `user` y `onLogout` como props** (datos y callback), y el cableado
  real —hacer `GET /api/auth/me` para el usuario, y `POST /api/auth/logout` + redirigir a `/login`— vive en
  una capa nueva **`src/features/auth/ui/AppShellClient.tsx`**. Regla de dependencia: `features/` consume
  `shared/ui`, nunca al revés.
- **Token-first y cero hardcode.** Se añadieron a `globals.css` los tokens del nav (alto, solape/elevación de
  carpetas, sombras, el 6º tono de carpeta) y, saldando una deuda de #12, el **namespace `--breakpoint-*`**
  que Tailwind v4 necesita para las variantes responsive (`tablet:`) — así ArchiveNav se muestra ≥ tablet y
  BottomNav < tablet **por token**, sin medidas sueltas. El guardrail `no-hardcode.test.ts` se extendió para
  escanear los 5 archivos nuevos y **fallar** ante cualquier valor crudo.

## El PORQUÉ — por qué así y no de otra forma

- **Pureza del design system:** meter el `fetch` dentro de `shared/ui` habría roto la portabilidad que fija el
  SDD §2 (el template no puede conocer los endpoints de *esta* app). Separar presentación (shared/ui) de
  wiring (features/auth/ui) mantiene el design system reutilizable y testeable en aislamiento.
- **Activa por ruta, no scroll:** en una SPA con rutas reales, la fuente de verdad de "dónde estoy" es la URL;
  el scroll-spy del template era para una página única de demostración.
- **`--breakpoint-*` como literales:** las media queries de CSS **no resuelven `var()`**, así que el namespace
  de breakpoints de Tailwind necesita valores literales; se dejaron compartiendo los mismos números que
  `--bp-*` (una sola verdad conceptual, dos formas de consumo).
- **No tocar `proxy.ts` ni el backend:** el acceptance lo prohíbe explícitamente ("proxy existente", "sin
  cambios de backend"). El conflicto conocido (ver deuda) se deja anotado, no se resuelve acá.
- **Alcance acotado:** no se construyeron el objeto 3D (feature #14), ni las 5 páginas de contenido (features
  19-30), ni las páginas login/register — cada cosa a su feature, un-feature-a-la-vez.

## Deuda o notas abiertas (no bloquean)

1. **`src/proxy.ts` con `/` público vs. Dashboard privado.** El Dashboard vive en `/` y por RFC es privado,
   pero `proxy.ts` lista `/` en `PUBLIC_PAGES`. **No se tocó** (fuera de alcance). A resolver cuando se cablee
   el flujo real de auth ↔ dashboard (¿Dashboard en `/` privado y una landing pública aparte? decisión de producto).
2. **Sin páginas login/register.** El grupo `(auth)` tiene su layout listo pero no hay páginas de auth; no
   existe feature explícita para ellas en `feature_list.json` — conviene decidir si se agregan como slice.
3. **Las 5 páginas de contenido** (`/proyectos`, `/lanas`, `/patrones`, `/calculadoras`, `/stash`) aún no
   existen (features 19-30); el nav ya las enlaza, correcto.
